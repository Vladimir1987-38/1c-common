# YAxUnit: подключение и работа с тестами

Дата проверки источников: 16.10.2026. Документ подготовлен в рамках PRJ-4263.

Это руководство по развёртыванию и использованию. Рабочий цикл агента описан в [общем навыке yaxunit](../skills/yaxunit/SKILL.md). 19.10.2026 цикл подготовки, адресной загрузки и запуска серверного теста проверен в Kassa 1C на YAxUnit 25.12 в толстом клиенте. Это не подтверждает установку и готовность остальных проектов. Разделы первоначальной установки ниже применяются, когда стенд ещё не настроен.

## Файлы в каждом проекте

19.10.2026 добавлен [общий комплект](../YAxUnit/README.md). Перед подключением получите исходники движка из [Wiki: YAxUnit](https://wiki.spb.teremok.ru/pages/viewpage.action?pageId=163548690) и восстановите 1c-common/YAxUnit/engine/25.12/YAXUNIT по инструкции общего комплекта; каталог engine не входит в Git. При подключении через tools/connect-project.ps1 создаются extensions/YAXUNIT, пустое extensions/Tests и tests/yaxunit с инструкцией, примером запуска и локальным test-config.local.json. Для уже подключённого проекта достаточно запустить skills/yaxunit/scripts/initialize-project.ps1 -ProjectRoot <путь>. Повторный вызов сохраняет существующие папки целиком, в том числе тесты кассы.

Подготовка исходников не устанавливает расширения в базу. Для загрузки XML/BSL нужен конфигуратор; готовый CFE движка доступен по ссылке ниже. Применимость проверяют в целевой тестовой базе. Tests из шаблона не содержит ни одного теста; успешный непустой прогон станет возможен после добавления тестов конкретного проекта. VAExtension относится к Vanessa и не требуется для YAxUnit.
## 1. Для чего использовать

YAxUnit запускает тестовые процедуры на встроенном языке 1С. Подходит для проверки вычислений, преобразования данных, условий, работы документов и регистров. Тест вызывает нужный метод и сравнивает результат с требованием.

| Инструмент | Основная роль в наших проектах |
|---|---|
| YAxUnit | Проверки алгоритмов и данных через код |
| Vanessa Automation | Проверки пользовательского пути через интерфейс |

Для YAxUnit движок и тесты устанавливаются в базу с проверяемой конфигурацией. Отдельная база менеджера Vanessa и её MCP-профиль не обеспечивают такое подключение. Схема будущего запуска:

~~~text
Разработчик или согласованный запуск агента
  → сеанс 1С тестовой базы проекта
    → расширение YAXUNIT
    → расширение Tests с тестами проекта
    → отчёт и результат прогона
~~~

Основание: [назначение и поддерживаемые режимы](https://bia-technologies.github.io/yaxunit/docs/getting-started/).

## 2. Версия и совместимость

Для воспроизводимого первого знакомства в примерах выбран опубликованный выпуск **25.12**, не предварительный релиз. Это выбранная версия инструкции, а не подтверждённая установка в любом проекте.

| Материал | Где получить |
|---|---|
| Готовый движок | [YAxUnit-25.12.cfe](https://github.com/bia-technologies/yaxunit/releases/download/25.12/YAxUnit-25.12.cfe) |
| Описание выпуска | [Релиз 25.12](https://github.com/bia-technologies/yaxunit/releases/tag/25.12) |
| Исходники для разработки/EDT | [Исходники 25.12](https://github.com/bia-technologies/yaxunit/tree/25.12), движок в exts/yaxunit |
| Основная документация | [Руководство YAxUnit](https://bia-technologies.github.io/yaxunit/) |

Smoke-25.12.cfe — отдельный файл выпуска для другого набора проверок; он не заменяет движок YAxUnit. Для описанного первого теста нужен именно YAxUnit-25.12.cfe.

Документация заявляет платформу 8.3.10+, Windows и Linux, файловые и клиент-серверные базы, тонкий и толстый клиент. Веб-клиент не поддерживается. У встроенного редактора тестов отдельные требования: Windows 8.3.14+, Linux 8.3.24+. Для первого подключения редактор и плагин EDT необязательны. Источники: [требования](https://bia-technologies.github.io/yaxunit/docs/getting-started/), [интерфейс](https://bia-technologies.github.io/yaxunit/docs/yaxunit-ui/).

В [метаданных движка 25.12](https://github.com/bia-technologies/yaxunit/blob/25.12/exts/yaxunit/src/Configuration/Configuration.mdo) указаны имя YAXUNIT и совместимость расширения 8.3.10. Версия установленной платформы и режим совместимости конфигурации — разные параметры. Проверка применимости в целевой тестовой базе обязательна до вывода о готовности; менять её совместимость по одной этой инструкции не требуется.

## 3. Что определить перед установкой

Заполните локальную карточку стенда:

- Точная тестовая база проекта, её версия и способ восстановления.
- Версия и разрядность платформы, толстый/тонкий клиент.
- Пользователь тестов и его права.
- Выбранный выпуск YAxUnit, имя собственного расширения тестов.
- Каталог исходников тестов и локальный каталог результатов.
- Возможные внешние действия проверяемого кода: оборудование, обмены, файлы.

Для первого теста достаточно проверки без записи в базу. Разрешение подготовить документацию не означает разрешение устанавливать расширения или подключаться к базе. Порядок действий агента остаётся по [общим правилам](../rules/workflow.md).

## 4. Установка через конфигуратор — будущий этап

1. Подготовьте отдельную тестовую копию нужной конфигурации.
2. Получите выбранный CFE из официального релиза.
3. В конфигураторе этой базы откройте «Конфигурация → Расширения конфигурации» и загрузите YAxUnit-25.12.cfe.
4. Убедитесь в активности расширения и проверьте применимость. Сохраните изменения, перезапустите тестовый сеанс.
5. Согласно инструкции YAxUnit, для **его расширения** необходимо отключить «Безопасный режим» и «Защиту от опасных действий». Это настройка инструмента в подготовленной тестовой базе, не рекомендация снимать ограничения со всех расширений.
6. Проверьте доступность раздела YAxUnit и команды запуска у пользователя тестов.

Если установка или запуск не проходят, сохраните точное сообщение и параметры совместимости. Не начинайте с автоматического изменения основной конфигурации или снижения совместимости движка.

При работе через EDT импортируйте проект движка из exts/yaxunit вне workspace, свяжите его с базовым проектом и обновите тестовую базу. Плагин упрощает запуск, но устанавливается отдельно. Основание: [установка](https://bia-technologies.github.io/yaxunit/docs/getting-started/install/).

## 5. Подключение тестов своего проекта

Для нашей организации работы предлагается отдельное расширение с **именем Tests**. Это позволяет заменять движок без смешивания с прикладными тестами. Размещение тестов внутри движка тоже поддерживается, но усложняет его обновление. [Варианты организации](https://bia-technologies.github.io/yaxunit/docs/getting-started/structure/).

После установки движка в будущем этапе:

1. Создайте в тестовой базе расширение Tests с совместимостью, подходящей её конфигурации.
2. Добавьте собственный общий модуль ТСТПроверкаПодключения. Не заимствуйте для этого прикладной общий модуль.
3. Для примера включите «Клиент (управляемое приложение)» и «Сервер». Глобальность и привилегированный режим не нужны. Сам тест регистрируется только для серверного выполнения.
4. Добавьте код из следующего раздела, сохраните расширение, проверьте его и перезапустите сеанс.
5. В настройках запуска укажите **имя** Tests, а не синоним и не имя CFE. Если расширение названо иначе, измените фильтр.

Единое размещение файлов проекта, создаваемое tools/connect-project.ps1:

~~~text
<проект>/
  extensions/
    YAXUNIT/                # Движок тестирования
    Tests/                  # Собственные тесты проекта
  tests/yaxunit/
    README.md               # Условия запуска и состояние стенда
    test-config.example.json
    test-config.local.json  # Локальные пути; исключён из Git
    results/                # Локальные отчёты; исключены из Git
~~~

Движок храните отдельно от исходников собственной конфигурации. Выбранную версию фиксируйте в README проекта. Секреты, базу 1С и временные результаты исключайте из Git. Скрипт connect-project.ps1 создаёт файлы YAxUnit и каркас Vanessa; установку в базу и проверку применимости выполняют отдельно.

## 6. Первый тест: обнаружение модуля и проверка результата

Пример проверяет длину строки без обращений к прикладным объектам и без записи данных. Он нужен для приёмки подключения, а не для оценки алгоритмов проекта.

В модуле ТСТПроверкаПодключения:

~~~bsl
#Область ПрограммныйИнтерфейс

// ---> SPB/Bulatov.V 16.10.2026 PRJ-4263 (фрагмент ДОБАВЛЕН) выполнено полностью codex
// Регистрирует серверную проверку подключения тестового модуля.
//
Процедура ИсполняемыеСценарии() Экспорт

	ЮТТесты.ДобавитьСерверныйТест("ДлинаСтрокиОбеда");

КонецПроцедуры // <--- SPB/Bulatov.V 16.10.2026 PRJ-4263

// ---> SPB/Bulatov.V 16.10.2026 PRJ-4263 (фрагмент ДОБАВЛЕН) выполнено полностью codex
// Проверяет работу утверждения на строке известной длины.
//
Процедура ДлинаСтрокиОбеда() Экспорт

	ДлинаТекста = СтрДлина("Обед");
	ЮТест.ОжидаетЧто(ДлинаТекста).Равно(4);

КонецПроцедуры // <--- SPB/Bulatov.V 16.10.2026 PRJ-4263

#КонецОбласти
~~~

Экспортная ИсполняемыеСценарии перечисляет тесты; имя в регистрации должно совпадать с экспортной тестовой процедурой. ДобавитьСерверныйТест ограничивает контекст выполнения сервером. В процедуре регистрации не создавайте документы и не выполняйте сам проверяемый алгоритм: она вызывается при обнаружении тестов. Основание: [первый тест](https://bia-technologies.github.io/yaxunit/docs/getting-started/first-test/), [регистрация](https://bia-technologies.github.io/yaxunit/docs/features/test-registration/).

Код приведён только в Markdown и не проверялся запуском платформы. При переносе примера в другую задачу оформите реквизиты изменений по действующим правилам проекта.

## 7. Ручной запуск и отладка

Откройте в 1С раздел YAxUnit → «Запуск тестирования», найдите нужный модуль и выполните только выбранный тест. Через «Сформировать настройки тестирования» можно подготовить файл запуска и командную строку. При скрытом разделе доступны средства «Все функции» / «Функции для технического специалиста» и обработка «Юнит-тесты». [Интерфейс YAxUnit](https://bia-technologies.github.io/yaxunit/docs/yaxunit-ui/).

Приёмка первого теста:

1. Правильное ожидание 4 даёт один успешный серверный тест.
2. Временно замените ожидание на 5: тот же тест должен завершиться ошибкой сравнения.
3. Верните 4 и повторите: снова успех.
4. Проверьте, что выполнялся именно ТСТПроверкаПодключения.ДлинаСтрокиОбеда; пустой список тестов успехом не считается.

Так проверяются обнаружение, выполнение и способность движка сообщать о несоответствии. Затем можно добавить тест выбранного реального метода по его требованиям.

Для отладки используйте конфигуратор с параметрами запуска либо плагин EDT. Режим EDT без перезапуска передаёт текст текущего тестового модуля; изменения других модулей требуют перезапуска. [Запуск и отладка](https://bia-technologies.github.io/yaxunit/docs/getting-started/run/).

## 8. Настройки и запуск из командной строки

Пример содержимого локального test-config.json:

~~~json
{
  "filter": {
    "extensions": ["Tests"],
    "modules": ["ТСТПроверкаПодключения"]
  },
  "reportFormat": "jUnit",
  "reportPath": "C:\\1C-Tests\\Runs\\first-run\\report.xml",
  "exitCode": "C:\\1C-Tests\\Runs\\first-run\\result.txt",
  "logging": {
    "file": "C:\\1C-Tests\\Runs\\first-run\\tests.log",
    "level": "info"
  },
  "closeAfterTests": false,
  "showReport": true
}
~~~

Заранее создайте каталог результатов, доступный сеансу 1С. Для каждого прогона используйте новый каталог, чтобы не принять старый отчёт за новый. Имена расширения и модуля должны совпадать с установленными объектами. Параметр exitCode — путь к файлу результата, а не код возврата процесса.

Пример команды для подготовленной файловой базы; заменить пути и версию платформы:

~~~text
"C:\Program Files\1cv8\<версия>\bin\1cv8.exe" ENTERPRISE /F "C:\1C-Tests\TestBase" /C "RunUnitTests=C:\1C-Tests\test-config.json"
~~~

Здесь запускается тестовая база проекта. /TESTMANAGER и /Execute обработки Vanessa для этого запуска не используются. Пользователя базы задайте локально привычным способом; пароль не включайте в общую инструкцию.

Для пакетного запуска укажите closeAfterTests=true и showReport=false. Завершение процесса само по себе не доказывает успех тестов: нужны свежий файл результата, отчёт и ненулевое число выполненных проверок. Значение 0 в файле exitCode означает успешное выполнение, 1 — наличие ошибок; отсутствие файла означает, что результата нет.

Поля сверены с [конфигурацией запуска выпуска 25.12](https://github.com/bia-technologies/yaxunit/blob/25.12/documentation/docs/getting-started/run/configuration.md), форма команды — с [руководством запуска](https://bia-technologies.github.io/yaxunit/docs/getting-started/run/).

Для дальнейшего управления агентом можно использовать согласованный запуск 1С и чтение результатов. В рамках подготовки документации такой исполнитель и MCP-интеграция YAxUnit не создавались. Существующий MCP Vanessa автоматически доступ к тестам YAxUnit не добавляет.

## 9. Тесты с данными

Для прикладного теста задайте входные данные, вызов реального метода и независимое ожидаемое значение. Не копируйте алгоритм проверяемого метода в вычисление ожидаемого результата.

YAxUnit позволяет выполнять серверный тест в отменяемой транзакции через ВТранзакции(). Для клиентских тестов этот режим игнорируется. Данные, созданные вне теста и охватываемых им событий, не попадают под такой откат. Альтернатива — механизм удаления данных, созданных через API движка, с его ограничениями. [Очистка данных](https://bia-technologies.github.io/yaxunit/docs/features/test-data/test-data-deletion/).

Откат транзакции базы не отменяет уже отправленный HTTP-запрос, запись файла или действие оборудования. В кассовых проектах границы таких действий определяют до запуска. Начинайте с чистых вычислений и методов без внешних последствий, затем переходите к данным и интеграциям.

## 10. Как разбирать ошибки

| Симптом | Что проверить |
|---|---|
| Не применяется CFE | Точный текст платформы, выбранную базу, версию и совместимость расширения |
| Нет раздела/команды YAxUnit | Активность расширения, права и перезапуск сеанса; доступ через технические функции |
| Тесты не найдены | Имя расширения в filter.extensions, модуль, ИсполняемыеСценарии, экспорт процедур |
| Метод ЮТест/ЮТТесты недоступен | Загрузку движка, контексты модулей и совместимость установленных расширений |
| Ошибка доступа или безопасного режима | Требования установки YAxUnit и права тестового пользователя |
| Проверка упала | Фактическое и ожидаемое значения, контекст и подготовленные данные |
| Процесс завершился без отчёта | Файл настроек, права на каталог, раннюю ошибку запуска; не считать это успешным тестом |
| Данные остались после теста | Клиентский/серверный контекст, область транзакции и способ создания данных |

При обновлении движка фиксируйте прежнюю версию, проверьте новый выпуск на отдельной копии и повторите первый тест с правильным и неверным ожиданиями, затем прикладной набор. Собственное расширение Tests и исходные условия должны быть воспроизводимы.

## 11. Что считать готовым подключением

- Движок и собственное расширение применяются к конкретной тестовой базе.
- Первый тест найден и выполняется в ожидаемом контексте.
- Правильное ожидание проходит, намеренно неверное обнаруживается.
- Получаются свежие отчёт и файл результата при пакетном запуске.
- Условия запуска и версия записаны в документации проекта.
- Хотя бы один реальный алгоритм покрыт отдельным тестом после выбора требования.

Создание этой инструкции не означает прохождение перечисленных проверок.

## Инструкция после проверки

После тестирования сохранить в tests/REPRODUCE.md конкретный ручной запуск текущего набора: меню YAxUnit, загрузку настроек, выбор тестов, ожидаемый состав, просмотр результата и очистку данных. Автоматическую команду приводить дополнительно. Жизненный цикл инструкции — по [общим правилам](../rules/workflow.md#инструкция-воспроизведения-тестирования); при новой задаче прежнее содержание архивируется либо удаляется.
