# YAxUnit в работе над доработками 1С

Используй для значимых проверок изменяемых алгоритмов и данных, а также по прямому поручению написать, загрузить или выполнить YAxUnit-тест. Для простых правок документации, оформления и других изменений без проверяемого поведения новый тест не нужен. Предпочитай существующие тесты проекта, добавляя проверку конкретного требования или исправляемой ошибки.

## Общая команда «Проверь доработку»

«Проверь доработку» и «Проверь эту доработку через YAxUnit» — равнозначные команды проверки текущей доработки через этот навык. Они относятся к текущему проекту и задаче из doc/PROMT.md, doc/MEMORY_BANK.md и фактических изменений; не выбирай произвольную старую задачу или весь набор тестов базы.

По команде определи проверяемое поведение, выбери существующие тесты и при необходимости подготовь недостающие. Выполни согласованный цикл адресной загрузки тестового расширения, запуска в тестовой базе проекта, проверки свежих результатов и восстановления сеансов. Итог команды — фактический результат с границами покрытия либо точная причина, по которой проверка не выполнена.

Уже выданные разрешения и установленные параметры проекта используй без повторных вопросов. Если неясны сама доработка, целевая база или допустимые действия, выясни недостающее до зависимых операций; до этого выполняй независимый анализ исходников. Команда не означает установку движка во всех базах, полную загрузку основной конфигурации, запуск всех тестов подряд или разрешение внешних платежей/отправок. Правила подключения и исполнения ниже сохраняются.

## Контекст проекта и границы действий

Работай по [общим правилам](../../rules/workflow.md) и doc/AGENTS.md текущего проекта. При продолжении текущей Jira-задачи не инициируй новый переход и не спрашивай повторно уже согласованные действия. Создание навыка или подключение точки входа не устанавливает движок и не разрешает автоматически изменять базы других проектов.

Перед кодом найди актуальные исходники, настройки tests/yaxunit, имя и каталог собственного расширения тестов, версию YAxUnit, разрешённую тестовую базу и тип клиента. Применяй локальную .1c-devbase через штатные инструменты, не читай и не печатай секреты. Название проекта, профиль Vanessa и пример из соседнего проекта не определяют целевую базу.

При первом подключении используй [руководство разработчика](<../../инструкции разработчику/YAxUnit.md>). Фиксируй в doc/AGENTS.md только проверенные проектные параметры: клиент, версия, имя/путь расширения, конфигурация запуска, ограничения и готовность. Не переноси правило «только толстый клиент» кассы на остальные проекты. Новому проекту с одной точкой входа присваивать готовность к тестам нельзя.

Подключение к базе, загрузка и запуск выполняются в пределах разрешений пользователя по общим правилам. Если поручено выполнить весь цикл в согласованной тестовой базе, продолжай его без повторных подтверждений на каждом шаге. Не устанавливай движок, не меняй основную конфигурацию и параметры защиты ради запуска без соответствующего объёма поручения.

## Подготовить проверку

1. Проследи штатный путь, обработчики записи и побочные действия. Раздели серверную проверку создания документа, проведение, оплату, внешнюю отправку и полный UI-сценарий. Не выдавай прохождение одного этапа за проверку всего бизнес-процесса.
2. Определи ожидаемые результаты из требования, а не из копии реализации. Для исправления ошибки воспроизведи условие регрессии; добавь значимые граничные случаи, если они относятся к изменению. Не подгоняй бизнес-ожидания под результат запуска.
3. Пиши тесты в собственном расширении проекта. Не правь YAXUNIT и VAExtension ради тестов. Сверяй типы реквизитов с метаданными, контексты модулей и доступные методы с исходниками установленной версии; соблюдай общие и личные стандарты BSL.
4. Для серверных проверок регистрируй ДобавитьСерверныйТест. Серверный код в клиент-серверном модуле защищай соответствующим условием компиляции. Сохраняй существующие тесты пользователя и UUID объектов.
5. Для записей в базу используй изолированные данные и ВТранзакции(), когда проверяемый код допускает откат. Сверь механизм отмены с установленной версией. Транзакция не отменяет печать, HTTP, файлы и уже запущенные фоновые задания: такие действия нужно исключить из теста, подменить в предусмотренной точке или отдельно согласовать интеграционный запуск. Не применяй ОбменДанными.Загрузка или другие обходы, если они отключат проверяемое поведение.
6. После штатного вызова перечитай записанный объект и проверь значимые свойства/движения. Явно укажи, какие данные синтетические и какие ветви настройки реально проверены.

## Загрузить и запустить

Подробности и проверенный синтаксис — в [исполнении и диагностике](references/execution.md). Операции платформы выполняй совместно с [1c-batch](../1c-batch/SKILL.md), состояние сеансов — по [1c-project-sync](../1c-project-sync/SKILL.md).

- Сохрани исходные сеансы и пользовательские изменения. Перед перезаписью модуля сверь свежую версию расширения в базе; не затирай несохранённый код.
- Загружай только перечисленные файлы тестовой доработки. Не включай корневые Configuration.xml/ConfigDumpInfo.xml основной конфигурации. Для новых объектов соблюдай проектные ограничения создания/заимствования; запрет на загрузку корня не обходи полной загрузкой расширения.
- Не заполняй недостающие прикладные изменения догадками: тест должен запускаться на нужной версии кода. Перенос прикладной доработки выполняй в её согласованном объёме.
- Используй новый сеанс подходящего клиента с RunUnitTests и явным фильтром. Фильтр modules выбирает модуль целиком: заранее установи точный состав тестов. Для автоматики обычно closeAfterTests=true, showReport=false; для ручного просмотра — false/true.
- На каждый прогон выделяй новые пути результатов либо убирай только собственные старые результаты. Зафиксируй UTC-время старта и PID. До завершения предыдущего прогона новый не запускай.
- При таймауте проверь процесс, окна и отчёт: таймаут ожидания не означает остановку теста. Не делай слепой повтор и не завершай пользовательские процессы принудительно.
- После операций восстанови исходные сеансы и тип клиента, независимо от исхода. Если у проекта настроено хранилище, восстанавливай конфигуратор через run-designer-repository.ps1. Обычный пользовательский сеанс восстанавливай без RunUnitTests. Передачу параметров хранилища отличай от подтверждённого доступа к его содержимому.

## Оценить результат

Используй [scripts/check-result.ps1](scripts/check-result.ps1): он читает только локальные отчёт и результат, проверяет свежесть, непустой состав, ожидаемые тесты, отсутствие ошибок и пропусков. Сам скрипт не запускает 1С и не подтверждает правильность бизнес-ожиданий.

Успех требует свежего корректного jUnit, фактического выполнения всех выбранных тестов без failure/error/skipped и файла результата 0. Код завершения процесса 1С, наличие окна, старый отчёт и ноль тестов успехом не являются. Ошибка компиляции/старта до тестов — сбой запуска, а не провал бизнес-проверки.

При ошибке установи категорию: окружение, неверная подготовка/утверждение теста или дефект продукта. Исправляй в согласованном объёме, сохраняя исходный смысл проверки. Если запуск не дошёл до теста, не заявляй, что алгоритм проверен. Повтор нужен после содержательного исправления, а не для получения желаемого статуса.

В конце укажи: что изменено и куда загружено, база/клиент без секретов, тесты и результаты, границы покрытия, очистка данных и восстановление сеансов. В doc/MEMORY_BANK.md сохрани краткий фактический итог; технические отчёты и временные материалы обрабатывай по общим правилам. Исходники тестов и конфигурации запусков остаются в проекте.
