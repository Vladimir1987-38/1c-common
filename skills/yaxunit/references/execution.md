# Исполнение и диагностика YAxUnit

Читайте при подготовке загрузки или запуска. Проверенная основа: YAxUnit 25.12 и платформа 8.3.20.1914; это не предписание версии или типа клиента для всех проектов. При другой версии сверяйте её исходники и официальную документацию. Метод ВТранзакции() в установленной 25.12 начинает транзакцию до теста и отменяет её после теста, включая ошибки утверждений.

## Подключение нового проекта

Перед созданием файлов восстановите общий движок из [Wiki: YAxUnit](https://wiki.spb.teremok.ru/pages/viewpage.action?pageId=163548690) в 1c-common/YAxUnit/engine/25.12/YAXUNIT. Проверка архива и структура — в [комплекте](../../../YAxUnit/README.md). Поставка движка не хранится в Git общей библиотеки; шаблон Tests и скрипты остаются в Git.

Точка входа создаётся общим tools/connect-project.ps1 из метаданных навыка. Это только обнаружение навыка. Для рабочего стенда отдельно нужны установленный и применимый YAXUNIT, собственное тестовое расширение и разрешённая база.

В doc/AGENTS.md проекта зафиксируйте:

- статус: не настроено / настроено, но не проверено / проверено, дату и результат;
- подтверждённый тип клиента (толстый или тонкий), версию платформы и YAxUnit;
- имя собственного расширения и путь его исходников (например, extensions/Tests);
- путь конфигурации запуска и каталог локальных результатов;
- особенности побочных действий и восстановления сеансов/хранилища.

Конкретные параметры базы и учётные данные остаются в локальной .1c-devbase. Не копируйте привязку кассы, профиль Vanessa, бизнес-тест обеда или расширения в остальные проекты автоматически. Общая инструкция установки — [YAxUnit.md](<../../../инструкции разработчику/YAxUnit.md>).

## Первое заполнение Tests после архивации

После [перехода к новой задаче](../../../rules/workflow.md#тесты-при-архивировании) проверить, что рабочее `extensions/Tests` содержит чистый каркас и только тесты новой задачи. Для первой согласованной загрузки использовать полный состав этого расширения через 1c-batch и проверить, что прежние модули удалены из установленного `Tests`. Частичная загрузка ниже предназначена для последующих изменений внутри одной задачи и не заменяет очистку состава при переходе. Основную конфигурацию, YAXUNIT и VAExtension эта операция не затрагивает.

## Частичная загрузка существующего модуля

Сначала выполните подготовку сеансов по 1c-project-sync, сохраните незагруженные изменения и проверьте фактический файл расширения. Если изменён только BSL, не грузите расширение целиком.

Штатный load-extension.ps1 поддерживает полную загрузку и не имеет параметра списка файлов. Для адресного переноса используйте общий Invoke-Designer из 1c-batch (из корня проекта). Пример ниже предполагает, что именно этот файл и Tests уже согласованы и существуют:

```powershell
& {
    . '../1c-common/skills/1c-batch/scripts/_common.ps1'
    . (Get-DevBasePath)
    $code = Invoke-Designer @(
        '/LoadConfigFromFiles', 'extensions/Tests',
        '-Extension', 'Tests',
        '-files', 'CommonModules/ТСТПроверкаПодключения/Ext/Module.bsl',
        '-Format', 'Hierarchical', '-updateConfigDumpInfo', '/UpdateDBCfg'
    )
    if ($code -ne 0) { throw 'Не удалось загрузить тестовый модуль' }
}
```

Имя/путь из примера заменяются фактическими. Здесь -Extension указан один раз: повтор после /UpdateDBCfg был отклонён платформой 8.3.20.1914. Не расширяйте набор переносимых объектов при ошибке параметров. Новые объекты требуют отдельного определения допустимого способа создания с учётом правил проекта, без выдумывания UUID.

После загрузки проверяйте её результат. При необходимости обратной выгрузки сравнивайте изменённые модули и актуализируйте только сведения выгрузки; не перезаписывайте чужие изменения.

## Запуск

Используйте проектный JSON с явно ограниченным filter.extensions/filter.modules. Для YAxUnit 25.12 workspacePath задаёт базовый путь, reportPath/exitCode/logging.file могут быть относительными. Формат отчёта — jUnit. Имя exitCode обозначает файл результата, а не код процесса 1С.

Для ручного запуска: в поле конфигуратора «Параметры запуска» передайте RunUnitTests=полный_путь_к_JSON без /C. Выберите нужный тип клиента. closeAfterTests=false и showReport=true оставляют сеанс для просмотра отчёта. После проверки верните прежние параметры запуска.

Для автоматического запуска используйте новый процесс выбранного клиента. /C нужен в командной строке, всё значение RunUnitTests вместе с путём передавайте одним аргументом. Применяйте локальные параметры подключения внутри области выполнения скрипта; не печатайте полную командную строку, если она содержит /P. Не передавайте параметры хранилища клиентскому сеансу.

Рабочая последовательность:

1. Подготовьте отдельные свежие пути результатов в каталоге проекта; не удаляйте чужие отчёты. Сохраните UTC-время непосредственно перед запуском: $startedAt = [DateTimeOffset]::UtcNow.
2. Примените .1c-devbase по правилам 1c-batch; выберите 1cv8.exe или 1cv8c.exe по проекту. Передайте ENTERPRISE, фактическое /F либо /S, учётные параметры и /C "RunUnitTests=...". Сохраните PID, но не секретные аргументы.
3. Ожидайте отчёт и завершение с конечным сроком, проверяя состояние интервалами не более 60 секунд. Длительность старта 1С и длительность самого теста различаются. Не запускайте параллельно другую пакетную операцию по той же базе.
4. При модальном окне сначала прочитайте текст. Подтверждать можно только понятный диалог в пределах поручения; не подтверждайте создание базы, изменение защиты или удаление данных ради продолжения теста.
5. Прочитайте результат скриптом ниже. При неуспехе сохраните первую существенную ошибку и название теста, установите причину. Повтор запуска допускается после исправления и установления исхода предыдущего процесса.
6. Восстановите исходные сеансы, обычный клиент без RunUnitTests, конфигуратор с параметрами хранилища при наличии. В отчёте отдельно фиксируйте недоказанное состояние соединения.

## Проверка результатов

Из корня проекта, с сохранённым временем старта именно этого прогона:

```powershell
& '../1c-common/skills/yaxunit/scripts/check-result.ps1' `
    -ReportPath 'tests/yaxunit/results/lunch-report.xml' `
    -ResultPath 'tests/yaxunit/results/lunch-result.txt' `
    -StartedAt $startedAt `
    -ExpectedTests @('ПроверкаДлиныСтроки', 'СозданиеЧекаОбедаСотрудника')
```

Подставляйте фактический план тестов, а не имена, прочитанные из отчёта. Скрипт требует совпадения состава имён, свежести обоих файлов и отсутствия пропусков/ошибок, не принимает пустой прогон. Если одинаковые имена выполняются в нескольких контекстах, дополнительно проверьте контексты/classname и ожидаемое количество: скрипт сравнивает имена, не контексты. Не используйте это как доказательство правильности проверок или полноты бизнес-сценария.

Разбирайте failure/error и журнал установленной версии; проверяйте assertion, подготовку данных и штатный код отдельно. Например, одинаковое отображение значения не означает одинаковый тип: реквизит Строка нельзя сравнивать со ссылкой справочника.

После результата запишите краткий содержательный итог и ограничения в проект. Созданные агентом машинные отчёты, логи и временные выгрузки удаляйте по общим правилам после окончания диагностики/восстановления; существующие пользовательские результаты не затрагивайте. Не удаляйте исходники тестов и настройки запусков.

После завершения сохранить в tests/REPRODUCE.md пошаговый ручной запуск именно текущего набора, необходимые настройки и ожидаемые результаты по [общему правилу](../../../rules/workflow.md#инструкция-воспроизведения-тестирования). Удаление технических отчётов не удаляет эту инструкцию.
