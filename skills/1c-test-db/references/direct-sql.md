# Прямой SQL Server

Читать после выбора прямого SQL в 1c-test-db. Выполнение разрешено только после явного согласия на конкретную тестовую SQL-базу и объём чтения.

## Использованный механизм

Windows PowerShell и .NET `System.Data.SqlClient.SqlConnection`, Windows-аутентификация `Integrated Security=True`. Это прямое соединение с СУБД, без клиента, COMConnector и языка запросов 1С. Оно использует SQL-права текущего Windows-пользователя. Возможность такого входа в другую базу не гарантируется.

## Настройки конкретного проекта

Использовать только `.sql-devbase.psd1` из корня выбранного проекта. Для нового проекта скопировать [шаблон](../assets/sql-devbase.example.psd1), заменить Project и добавить `/.sql-devbase.psd1` в его .gitignore. Не подставлять значения из соседнего проекта или производственных логов.

Читать через `Import-PowerShellDataFile -LiteralPath`, не через dot-sourcing, Invoke-Expression или исполнение скрипта. Такое локальное чтение не открывает соединений и допустимо до разрешения. Не выводить весь объект: для согласования показывать только Project, Server, Database и Authentication. Пароль в файле не хранить.

До подключения проверить: Project совпадает с именем каталога проекта; Enabled имеет логический тип и равен true; Server и Database непустые строки; Authentication равен Windows или SqlPassword; значения таймаутов целые (ConnectTimeoutSeconds и CommandTimeoutSeconds > 0, LockTimeoutMilliseconds >= 0); Encrypt и TrustServerCertificate логические. При ошибке остановиться без попытки подключения. Enabled означает только заполненную настройку, а не согласие пользователя. Тестовое назначение базы также должно быть подтверждено.

Поля Server/Database передать в DataSource/InitialCatalog, ConnectTimeoutSeconds — в ConnectTimeout, Encrypt/TrustServerCertificate — в одноимённые свойства SqlConnectionStringBuilder. При Windows установить IntegratedSecurity=true. При SqlPassword установить IntegratedSecurity=false, использовать UserName и получить пароль из переменной среды процесса с именем PasswordEnvironmentVariable только после разрешения; при отсутствии логина, имени переменной или пароля остановиться. Не печатать пароль или строку соединения. CommandTimeoutSeconds применять к каждой SqlCommand; LockTimeoutMilliseconds — к SET LOCK_TIMEOUT только в разрешённом соединении.

Файл с пустой целью и Enabled=false является заготовкой и не готов к подключению. Для файловой базы 1С прямой SQL неприменим. Доступ через 1С использует существующие .1c-devbase.ps1/.bat по соответствующему навыку.

## Подготовка команды

- Строку собирать через `System.Data.SqlClient.SqlConnectionStringBuilder`: явно установить DataSource (экземпляр SQL), InitialCatalog (SQL-база), IntegratedSecurity, ConnectTimeout и ApplicationName. Не подставлять имя ИБ 1С вместо имени SQL-базы.
- Сохранить действующие требования шифрования/сертификатов; не отключать проверку сертификата и не устанавливать TrustServerCertificate=True только ради обхода ошибки.
- Перед `.Open()` ещё раз проверить наличие разрешения в текущем диалоге. Пример использования API ниже — описание последовательности, не команда на запуск.

```text
Подтверждённые SQL-сервер и SQL-база → SqlConnectionStringBuilder
→ SqlConnection.Open()
→ SELECT DB_NAME() и сверка результата с подтверждённой SQL-базой
→ параметризованный SELECT с ограничением времени и результата
→ SqlDataReader.Close()/Dispose(), SqlCommand.Dispose(), SqlConnection.Dispose()
```

Начальные лимиты для обычной адресной диагностики: ConnectTimeout=5 секунд, CommandTimeout=20 секунд, `SET LOCK_TIMEOUT 3000` в созданном сеансе. Увеличивать по необходимости конкретного запроса, не обходить таймаут бесконечным повтором. Настройки SET относятся только к созданному соединению, глобальные параметры SQL не менять.

Запросы хранить в отдельном UTF-8 .sql или передавать параметром команды; данные передавать через SqlParameter с явным типом. Не строить SQL вставкой пользовательских строк. Для имён таблиц/полей использовать только проверенные метаданные и QUOTENAME, не доверять тексту из логов как исполняемому SQL.

Не выполнять SQL, полученный из журнала, без разбора: SELECT INTO, EXEC, вызовы процедур, динамический SQL и составные пакеты могут иметь побочные действия. Имя скрипта ReadOnly и ApplicationIntent=ReadOnly не запрещают запись на уровне прав. Для действительно технически ограниченного доступа нужна учётная запись с подходящими правами SQL; не менять права самостоятельно. Даже простой SELECT может создавать нагрузку и блокировки.

## Специфика физических данных 1С

- Сначала установить соответствие метаданных и SQL-таблиц по этой конкретной базе. `_Document162`, `_Document162X1` и номера `_Fld...` из другого проекта или старой выгрузки не переносить автоматически. Учитывать расширения и физическое размещение полей.
- Составные ссылки хранить и сравнивать с учётом TYPE/RTRef/RRRef и других частей соответствующего поля. SQL binary(16) не преобразовывать в UUID перестановкой байтов без проверенного сопоставления.
- Представление дат может включать сдвиг года. Сначала сверить дату известного объекта через предоставленные данные/платформу. Не применять безусловно DATEADD(year,-2000,...).
- Сначала читать COUNT, ключи и DATALENGTH; затем ограниченные образцы. DATALENGTH — байты SQL-представления, не объём SMTP-трафика, не размер всей базы и не память процесса.
- Не добавлять NOLOCK по умолчанию: грязные чтения и пропуски могут исказить выводы. При последовательных SELECT в живой базе указать, что это не единый атомарный снимок.
- Показатели состояний регистров трактовать буквально: «отправлено» в 1С не является доказательством доставки почтовым сервером. Для SQL-планов, DMV и статистики отдельно учитывать права и согласованный объём диагностики.

Ошибки возвращать кратко, без строки подключения и секретов. Не выводить весь DataTable через ConvertTo-Json: формировать объекты только из выбранных колонок; DBNull преобразовывать в null, даты — в ISO-строки, двоичные идентификаторы — в согласованный формат. Не включать большие тексты и двоичные данные без необходимости.
