# Доступ через платформу 1С

Выбирать, когда нужны язык запросов 1С, имена метаданных, поведение объектов или ограничения доступа платформы. Разрешение на прямой SQL не разрешает автоматически этот способ: создание сеанса может выполнять код инициализации конфигурации.

## Подготовка

- Подтвердить тестовую цель: сервер 1С/имя ИБ либо путь файловой базы, учётную запись и требуемые действия. SQL-адрес и пароль не являются реквизитами входа в 1С.
- Использовать настройки текущего проекта по [1c-batch](../../1c-batch/SKILL.md); содержимое секретных файлов не выводить. Запуск и синхронизацию выполнять через [1c-project-sync](../../1c-project-sync/SKILL.md), а не дублировать их скрипты.
- Предпочитать уже предусмотренную проектом консоль запросов или диагностическую обработку. Подготовить файл запроса/обработки до подключения. Не создавать HTTP-сервис или публикацию только ради одного запроса.
- Если требуется COMConnector, сначала после разрешения проверить локальную доступность совместимой версии и разрядность процесса/компоненты. Использовать V83.COMConnector.Connect для конкретной подтверждённой цели; строку соединения формировать безопасно в памяти, не выводить и не передавать пароль открытой командной строкой. Не регистрировать COM и не устанавливать платформу автоматически. При отсутствии компоненты сообщить ограничение, не переходить молча к SQL.

## Запросы и сценарии

Через соединение 1С создавать объект Запрос, задавать текст и типизированные параметры, выполнять выборку только нужных полей. Ссылки получать штатными средствами 1С. SQL-таблицы `_InfoRg...` здесь не использовать вместо имён метаданных. Ограничения доступа зависят от пользователя и контекста сеанса; привилегированный режим для диагностики не включать автоматически.

Проверка записи документа, проведения, бизнес-правил и других операций — отдельный разрешённый объём. До выполнения определить конкретные тестовые объекты и ожидаемые изменения. Учесть возможные внешние эффекты: письмо, HTTP-запрос, обмен и фоновое задание могут обращаться к рабочим системам даже из тестовой базы. Не запускать такой сценарий без согласованных тестовых адресатов/контура; не менять настройки интеграции молча.

У сеансов/COM-вызовов ограничивать время ожидания на уровне выбранного инструмента. По завершении освобождать созданные COM-объекты и собственный сеанс. Не убивать чужие процессы и не обещать откат внешних отправок обычным откатом транзакции.

В результате явно указать: запрос исполнен платформой или проверен только синтаксически; под каким согласованным контекстом; какие объекты/поля прочитаны или изменены. Само наличие этого руководства не означает, что COM или функциональный сценарий уже проверен на целевой базе.
