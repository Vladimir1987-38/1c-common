# Диагностика MCP Vanessa

Читать при неполном списке инструментов, ошибке подключения либо расхождении между каталогом чата и формой управления MCP. Сначала проверить уже имеющиеся ответы и локальные настройки. Любое новое обращение к базе/Vanessa остаётся в пределах разрешения из SKILL.md.

## Где искать причину

| Наблюдение | Что установлено | Следующее действие |
|---|---|---|
| infobase_info отвечает, других инструментов в чате нет | Работает один вызов MCP; доступность Vanessa ещё не проверена | Сопоставить адрес и список tools/list на том же сервере |
| В управлении MCP инструменты включены | Они зарегистрированы в показанном сеансе менеджера | Проверить, что Codex обращается к тому же адресу и порту |
| Сервер отдаёт больше инструментов, чем каталог чата | Каталог чата не соответствует серверу | Использовать разрешённую прямую диагностику; при необходимости предложить обновить подключение/сеанс Codex |
| get_vanessa_automation_state сообщает только о загруженном feature | Vanessa отвечает, подробного состояния теста нет | Не запускать тест ради диагностики; проверить окна клиента |
| ACTION_FAILED: Клиент тестирования не подключен | MCP и Vanessa доступны, связи с клиентом нет | Подключить правильный профиль только в пределах поручения |
| Окна относятся к другой базе | Цель проверки не совпадает | Остановиться до уточнения, не переключать базу самостоятельно |

Число инструментов и порт не являются постоянными критериями. Не диагностировать ошибку Vanessa только потому, что текущая версия отдаёт другой состав инструментов.

## Адрес и ограничения Codex

Сопоставить настроенный URL с портом формы управления MCP и сеансом менеджера. Проверять только релевантную секцию mcp_servers или настройку MCP соответствующего плагина. Не выводить полный config.toml, токены и заголовки. Не выполнять файлы настройки 1С ради получения адреса.

Учитывать enabled, enabled_tools и disabled_tools, а также применимые настройки проекта и политики. Включённый сервер может отдавать в чат только разрешённую часть инструментов. Если ограничение задано явно или действие отклонено по доступу, не обходить его прямым HTTP-вызовом.

При локальной ошибке среды выполнения отделять её от ответа MCP: ошибка запуска PowerShell не доказывает недоступность Vanessa. Использовать разрешённый способ запуска либо сообщить ограничение; не менять политики безопасности.

## Прямой вызов того же MCP

Использовать как резервную диагностику, когда встроенный каталог неполон и отсутствует явный запрет на нужное действие. Это тот же MCP, не SQL, COM или произвольное выполнение BSL. Сохранять согласованный адрес, клиента и объём чтения. Не искать рабочий сервер перебором портов.

Предпочитать уже имеющийся проверенный MCP-клиент. Если его нет, воспроизвести стандартный обмен Streamable HTTP:

1. POST initialize с jsonrpc = "2.0", уникальным id, поддерживаемой protocolVersion, capabilities = {} и clientInfo. В проверенном окружении работала версия протокола 2024-11-05; это пример совместимости, а не требование ко всем серверам. Проверить согласованную версию в ответе.
2. Сохранить полученный Mcp-Session-Id, если сервер его вернул, и передавать в последующих запросах. Не печатать идентификатор сеанса. Передавать согласованный MCP-Protocol-Version согласно версии транспорта.
3. Отправить notifications/initialized без id; отсутствие тела ответа на уведомление допустимо.
4. Выполнить tools/list. Прочитать имена, описания, inputSchema; при nextCursor получить оставшиеся страницы. Не считать каталог инструментов результатом их выполнения.
5. После проверки схемы вызвать tools/call только для разрешённого чтения. Для get_vanessa_automation_state и get_window_list_testclient на проверенном сервере arguments были пустым объектом; перед повторным использованием сверить текущую схему.
6. Разобрать JSON-RPC error и result.isError. HTTP 200 сам по себе не означает успех. Сообщения ACTION_FAILED в содержимом также не выдавать за успешную проверку.

Для HTTP задавать Content-Type: application/json и Accept: application/json, text/event-stream. Сервер может вернуть обычный JSON либо SSE. В SSE собрать data-строки события и найти ответ с id своего запроса; уведомления не принимать за результат. Ограничивать ожидание, не оставлять бесконечный HTTP-запрос.

В Windows PowerShell 5.1 response.Content может исказить кириллицу, если сервер не указал кодировку. Для ответа Invoke-WebRequest -UseBasicParsing в проверенном окружении использовалось декодирование байтов:

~~~powershell
$responseText = [System.Text.Encoding]::UTF8.GetString(
    $response.RawContentStream.ToArray()
)
~~~

Не исправлять неверно декодированный текст заменой букв. Сохранить правильное чтение UTF-8 до ConvertFrom-Json.

Примеры тел запросов после инициализации; перед вызовом проверить адрес, разрешение и актуальную схему:

~~~json
{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}
{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"get_vanessa_automation_state","arguments":{}}}
{"jsonrpc":"2.0","id":4,"method":"tools/call","params":{"name":"get_window_list_testclient","arguments":{}}}
~~~

При ошибке авторизации, несовпадении цели или таймауте остановить попытку и сообщить фактический результат. Не повторять команды запуска/изменения как способ проверки транспорта. Прямой успешный вызов не означает, что встроенный каталог Codex уже обновился.

Источники: [жизненный цикл MCP](https://modelcontextprotocol.io/specification/2024-11-05/basic/lifecycle), [Streamable HTTP](https://modelcontextprotocol.io/specification/2025-03-26/basic/transports), [MCP в Codex](https://developers.openai.com/codex/mcp/).
