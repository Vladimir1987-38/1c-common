# Общие стандарты разработки 1С

Обязательные требования для всех подключённых проектов. Документ объединяет общие правила 1С и корпоративные стандарты из Wiki. Личные предпочтения по оформлению и маркировка изменений находятся в [личных настройках и стандартах](personal-standards.md).

Перед каждым новым этапом изменения кода читать актуальные редакции обоих документов. Перед завершением проверять все изменённые фрагменты по применимым требованиям. Постоянные источники находятся в общей папке rules; копии стандартов в проектах не создавать.

Примеры показывают отдельные требования и могут быть неполными. Предметные значения, формулы, имена объектов и реквизиты задач из примеров не переносить в рабочий код без требований текущей задачи. Рекомендации и исключения отмечены отдельно от обязательных правил.

Порядок работы, согласование подключений, ведение контекста и использование навыков определены в [общих правилах](workflow.md).

## Задача и границы изменений

Доработки выполнять только с номером задачи Jira. Если номер неизвестен, запросить его до начала доработки; до получения номера изменения не вносить. Номер не выдумывать. Прежнее разрешение на техническую работу без номера не заменяет номер задачи.

До изменения кода определить затронутые сценарии, контексты исполнения, метаданные и ожидаемый результат. Переиспользовать существующие интерфейсы и бизнес-правила. Вносить только необходимые изменения. Общие правила, навыки и скрипты изменять в 1c-common; код конфигурации и проектные особенности — в соответствующем проекте.

Оформление добавлений, изменений и удалений выполнять по разделу «Маркировка изменений» [личных стандартов](personal-standards.md#маркировка-изменений).

## Оформление BSL

- Использовать осмысленные русскоязычные имена. Процедуры и функции именовать с заглавной буквы.
- Соблюдать существующие области и структуру модуля; отделять экспортный интерфейс от служебного кода.
- Использовать табуляцию в стиле проекта, не оставлять пробелы и табуляции в конце строк.
- Размещать один оператор в одной строке; длинные условия переносить по смысловым частям.
- Комментировать причину или бизнес-правило, а не пересказывать очевидный код.
- Описывать все процедуры и функции программного интерфейса; остальные методы рекомендуется описывать, если требуется пояснение назначения или особенностей работы.
- Использовать фактические номер задачи, автора и дату; соблюдать маркировку из личных стандартов.
- Не хранить закомментированный код без документированной причины.

ИТС: [тексты модулей](https://its.1c.ru/db/v8std/content/456/hdoc), [структура модуля](https://its.1c.ru/db/v8std/content/455/hdoc), [описание процедур и функций](https://its.1c.ru/db/v8std/content/453/hdoc), [имена переменных](https://its.1c.ru/db/v8std/content/454/hdoc), [конструкции языка](https://its.1c.ru/db/v8std/content/441/hdoc).

### Описание процедур и функций

Описывать назначение и контракт метода: что получает вызывающий код, какие значения допускаются и что означает отказ. Начинать описание с глагола: «Возвращает», «Проверяет», «Записывает». Не пересказывать имя метода и очевидные строки реализации.

- В области ПрограммныйИнтерфейс описание обязательно для всех добавленных и изменённых в рамках задачи процедур и функций, а не только для методов, отдельно указанных пользователем.
- Для служебных методов и обработчиков в других областях описание рекомендуется, если нужно пояснить назначение, сложность или особенности работы. Простой метод с понятным назначением допускается не описывать. Содержательные пояснения внутри алгоритмов сохранять.
- Размещать описание перед объявлением метода, в модуле формы — перед директивой контекста. Пустые строки внутри описания оформлять как строку с двумя косыми чертами.
- В разделе «Параметры:» перечислять точные имена, типы и назначение параметров. Указывать допустимые пустые значения, значения по умолчанию и изменение переданного параметра, когда это существенно. Звёздочка обозначает вложенные свойства, а не сами параметры.
- Для функции добавлять «Возвращаемое значение:» с типом и смыслом результата; для процедуры этот раздел не нужен. Явно описывать Ложь, пустую строку, пустую таблицу и Неопределено, если они предусмотрены контрактом. Для разных типов результата перечислять варианты отдельными строками с дефисом.
- Для структуры и таблицы значений раскрывать используемые свойства/колонки: звёздочка, имя, тип, назначение. Для уже описанного контракта допустима точная ссылка «см. Модуль.Метод»; ссылка должна вести к актуальному описанию.
- Указывать существенные побочные действия, условия отказа и исключения. Не обещать в комментарии проверок или гарантий, которых нет в коде. При изменении контракта актуализировать описание.
- Не добавлять пустые разделы и бессодержательные комментарии. При поручении изменить только комментарии сохранять сигнатуры, директивы контекста и весь исполняемый код.

Пример полного описания функции поиска (контракт из задачи FUS-288):

~~~bsl
// Возвращает локальные карты кассиров и администраторов по началу ФИО владельца.
// Исключает удалённые карты и владельцев, а также карты, не принадлежащие сотрудникам.
// Не подтверждает право входа: перед входом требуется отдельная проверка выбранной карты.
//
// Параметры:
//  ФИО - Строка - начало ФИО без учёта пробелов по краям.
//   Пустое значение возвращает таблицу без строк.
//
// Возвращаемое значение:
//  ТаблицаЗначений - найденные карты, упорядоченные по ФИО владельца:
//   * ИнформационнаяКарта - СправочникСсылка.ИнформационныеКарты - найденная карта.
//   * ВладелецКарты - СправочникСсылка.ВладельцыИнформационныхКарт - владелец карты.
//   * ДатаРождения - Дата - дата рождения владельца.
//   * СостояниеКарты - ПеречислениеСсылка.СостоянияИнформационныхКарт - роль карты.
//   * ВидКарты - Строка - представление состояния карты для показа пользователю.
//
// Пример:
//  НайденныеКарты = Справочники.ИнформационныеКарты.КартыКассировДляАварийногоВхода("Иванов");
//  // Таблица содержит подходящие локальные карты или не содержит строк.
Функция КартыКассировДляАварийногоВхода(ФИО) Экспорт
	// Реализация поиска.
КонецФункции
~~~

Если результат имеет несколько типов, оформлять его, например, так:

~~~bsl
// Возвращаемое значение:
//  - ПеречислениеСсылка.СостоянияИнформационныхКарт - проверенная роль кассира или администратора.
//  - Неопределено - аварийный режим выключен, карта недоступна либо её владелец или роль изменились.
~~~

Основание: стандарты 1С [«Описание процедур и функций»](https://its.1c.ru/db/content/v8std/src/400/100/i8100453.htm) и [«Структуры и таблицы значений в качестве параметров процедур и функций»](https://its.1c.ru/db/content/v8std/src/400/100/i8100641.htm).

В описании при необходимости добавлять пример вызова с именем общего модуля и понятным результатом. Для переопределяемого модуля показывать пример реализации переопределяемого метода. Для нескольких комбинаций типов допустима секция «Варианты вызова». Описание устаревшего метода начинать словом «Устарела». Ссылки внутри текста заключать в круглые скобки; если описание состоит только из ссылки, скобки не нужны.

Корпоративный источник также упоминает обработку ФорматированиеДирективКомпиляции.epf для упорядочивания комментариев и директив через выгрузку и загрузку модулей. Её наличие и работоспособность при объединении стандартов не проверялись.

Корпоративный источник: [Описание процедур и функций](https://wiki.spb.teremok.ru/pages/viewpage.action?pageId=163548231).

### Использование структур

Для читаемости и удобства сопровождения рекомендуется:

1. Не передавать в конструктор структуры более трёх значений свойств. При большем количестве использовать `Вставить` или явные присваивания свойствам.
2. Не вкладывать в конструктор структуры конструкторы других объектов, если они принимают параметры; в частности, не создавать внутри другую структуру с заданными значениями свойств.
3. Не вызывать в конструкторе структуры функции, у которых больше трёх параметров.

Пример оформления с последовательным заполнением:

~~~bsl
НастройкиОтчета = Новый Структура;
НастройкиОтчета.Вставить("НачалоПериода", НачалоПериода);
НастройкиОтчета.Вставить("КонецПериода", КонецПериода);
НастройкиОтчета.Вставить("Организация", Организация);
НастройкиОтчета.Вставить("ПоказыватьИтоги", Истина);
~~~

Это иллюстрация способа заполнения. В подключённых проектах дополнительно соблюдать [личное правило выделения конструкторов](personal-standards.md#конструкторы-и-заполнение-коллекций).

Источник: [Использование объектов типа Структура](https://wiki.spb.teremok.ru/pages/viewpage.action?pageId=163548232).

## Архитектура, модули и контексты

### Ответственность модулей

- Размещать код в модуле, соответствующем его ответственности; не переносить бизнес-логику в форму.
- Перед созданием функции искать существующую реализацию и ее вызовы.
- Общее бизнес-правило должно иметь одно место определения.
- Экспортировать только необходимый интерфейс и не добавлять скрытые побочные эффекты.
- Проверять свойства контекста общего модуля: клиент, сервер, внешний вызов и повторное использование.
- Не устанавливать «Вызов сервера» без необходимости.

ИТС: [дублирующий код](https://its.1c.ru/db/v8std/content/440/hdoc), [общие модули](https://its.1c.ru/db/v8std/content/469/hdoc), [выбор вида модуля](https://its.1c.ru/db/v8std/content/486/hdoc), [признак «Вызов сервера»](https://its.1c.ru/db/v8std/content/679/hdoc).

### Клиент и сервер

- Оставлять на клиенте интерфейсную логику; работу с базой и бизнес-логику выполнять на сервере.
- Минимизировать серверные вызовы и не выполнять их в цикле без необходимости.
- Не передавать лишние поля, большие коллекции и объекты, если достаточно ссылки или структуры.
- Не полагаться на состояние клиентской формы в серверной логике.

ИТС: [серверные вызовы и трафик](https://its.1c.ru/db/v8std/content/487/hdoc), [код на клиенте](https://its.1c.ru/db/v8std/content/629/hdoc), [безопасность серверного API](https://its.1c.ru/db/v8std/content/678/hdoc).

## Запросы и данные

- Передавать внешние значения только через параметры запроса; не собирать запрос конкатенацией данных.
- Явно перечислять поля и задавать понятные псевдонимы.
- Использовать `ОБЪЕДИНИТЬ ВСЕ`, если удаление дублей не требуется.
- Условия виртуальных таблиц задавать в их параметрах, когда это возможно.
- Избегать разыменования составных ссылочных полей и сложных соединений без оценки объема данных.
- Для многоэтапной обработки использовать временные таблицы и при необходимости индексы.
- Не выполнять однотипный запрос в цикле; несколько реквизитов читать одним обращением.

ИТС: [оформление запросов](https://its.1c.ru/db/v8std/content/437/hdoc), [оптимальные запросы](https://its.1c.ru/db/v8std/content/729/hdoc), [однотипные запросы](https://its.1c.ru/db/v8std/content/436/hdoc), [эффективные условия](https://its.1c.ru/db/v8std/content/658/hdoc), [виртуальные таблицы](https://its.1c.ru/db/v8std/content/657/hdoc), [временные таблицы](https://its.1c.ru/db/v8std/content/777/hdoc).

### Однотипные данные

Рекомендуется получать необходимые однотипные данные одним запросом вместо выполнения серии запросов в цикле.

ПРАВИЛЬНО — передать коллекцию значений в условие `В (&БанкиДляОбработки)`:

~~~bsl
ОбщийЗапрос = Новый Запрос;
ОбщийЗапрос.Текст =
"ВЫБРАТЬ
|	БанковскиеСчета.Ссылка КАК Счет
|ИЗ
|	Справочник.БанковскиеСчета КАК БанковскиеСчета
|ГДЕ
|	БанковскиеСчета.Банк В (&БанкиДляОбработки)";

ОбщийЗапрос.УстановитьПараметр("БанкиДляОбработки", БанкиДляОбработки);
ВыборкаСчетов = ОбщийЗапрос.Выполнить().Выбрать();

Пока ВыборкаСчетов.Следующий() Цикл
	ОбработатьСчетаВБанке(ВыборкаСчетов.Счет);
КонецЦикла;
~~~

НЕПРАВИЛЬНО — в цикле по банкам заново выполнять запрос с условием `Банк = &Банк`, когда нужные данные можно получить одним запросом.

Источник: [Многократное выполнение однотипных запросов](https://wiki.spb.teremok.ru/pages/viewpage.action?pageId=163548226).

### Объём выборки и сложность

Выбирать ровно те строки и поля, которые нужны для задачи. Не использовать `ВЫБРАТЬ *` для получения полей «на всякий случай».

Перед выборкой большого объёма данных для последующей свёртки, сортировки и вычислений на сервере 1С оценить возможность получить готовый результат средствами запроса. В большинстве случаев минимизировать и общее количество запросов к СУБД.

При этом не переносить всю обработку в один сложный запрос любой ценой. Рассматривать:

- Несколько более простых текстов запроса в зависимости от условий и значений параметров.
- Обработку выбранных данных средствами встроенного языка на сервере 1С.

Запрос должен использовать эффективный план выполнения. Не усложнять его без необходимости:

- Не добавлять вложенные запросы только ради читаемости.
- Избегать сложных условий соединения и отбора, особенно с подзапросами и конструкциями `ВЫБОР`.
- Использовать минимально необходимое число таблиц.

Упомянутые в источнике 5–7 таблиц — пример количества, при котором запрос уже может стать сложным для оптимизатора, а не установленный предел.

Источник: [Общие требования по разработке оптимальных запросов](https://wiki.spb.teremok.ru/pages/viewpage.action?pageId=163548227).

### Индексы и условия

Проверять наличие подходящих индексов для условий в секциях `ГДЕ`, `ПО`, параметрах виртуальных таблиц и `ИМЕЮЩИЕ`.

По формулировке источника подходящий индекс содержит все поля условия в начале индекса, подряд, без полей, которые в условии не участвуют. Если начальные поля индекса не заданы, быстрый поиск может оказаться невозможен; если пропущено поле внутри начальной последовательности, индекс может использоваться только частично.

Сначала учитывать индексы, которые платформа создаёт автоматически:

- По ссылке для объектных сущностей.
- По регистратору для движений регистров, подчинённых регистратору.
- По периоду и измерениям для итоговых таблиц регистров накопления.
- По периоду, счёту и измерениям для итоговых таблиц регистров бухгалтерии.

Если их недостаточно, рассмотреть дополнительное индексирование реквизитов. Реквизиты справочников и документов рекомендуется индексировать с дополнительным упорядочиванием, чтобы индекс учитывал основное представление объекта.

Создавать индекс только под известный запрос: ускорение поиска может замедлить добавление, изменение и удаление данных. Не создавать индексы «на всякий случай» и заведомо избыточные индексы.

В частности, по источнику:

- Не индексировать дополнительно первое измерение регистра, если поиск уже обеспечивает основной индекс таблицы итогов.
- Не индексировать поля с малым разнообразием значений без обоснования. Для `Булево` индекс может иметь смысл, когда одно значение встречается у небольшой части записей и запросы выбирают именно её.

Источник: [Несоответствие индексов и условий запроса](https://wiki.spb.teremok.ru/pages/viewpage.action?pageId=163548228).

### Ссылки составного типа

Обращение к полю через точку создаёт неявное соединение с таблицей ссылочного объекта. При составном типе соединения могут возникнуть со всеми таблицами возможных типов ссылки, а при RLS — также с таблицами ограничений доступа.

Получение реквизитов через ссылку составного типа крайне нежелательно; каждое исключение требует отдельного анализа.

Пример из источника:

~~~bsl
ТоварныеЗапасы.Регистратор.Дата
~~~

Такое обращение может присоединить таблицы всех документов — регистраторов регистра.

Способы уменьшить число соединений:

- Задавать для ссылочного поля только действительно необходимые типы; избегать «любой ссылки» и «ссылки на любой документ» без необходимости.
- Ограничивать тип в конкретном запросе функцией `ВЫРАЗИТЬ`.
- Если универсальный запрос вызывается в разных условиях, формировать его с приведением к нужному в этих условиях типу.
- При необходимости хранить нужное значение в исходной таблице, принимая обоснованное дублирование данных ради производительности.

Пример последнего подхода из источника: реквизит регистра `ДатаРегистратора`, который заполняется при проведении и используется вместо `Регистратор.Дата`.

Источник: [Разыменование ссылочных полей составного типа в языке запросов](https://wiki.spb.teremok.ru/pages/viewpage.action?pageId=163548229).

## Метаданные и отчёты

- Давать объектам имена, синонимы и комментарии по назначению.
- Выбирать минимально достаточный тип и длину; избегать составных типов без основания.
- Не переименовывать и не удалять объект без анализа совместимости, обменов и обновления данных.
- Для нового предопределенного элемента учитывать обновление существующих баз.
- Не менять идентификаторы метаданных вручную.

ИТС: [имена объектов](https://its.1c.ru/db/v8std/content/550/hdoc), [имя, синоним, комментарий](https://its.1c.ru/db/v8std/content/474/hdoc), [строковые реквизиты](https://its.1c.ru/db/v8std/content/432/hdoc), [составные типы](https://its.1c.ru/db/v8std/content/728/hdoc), [предопределенные элементы](https://its.1c.ru/db/v8std/content/697/hdoc).

### Имена и представления новых объектов

При добавлении нового объекта заполнять свойства по следующей таблице.

| Свойство | Обязательное заполнение | Символ `_` в начале |
| --- | --- | --- |
| Имя | Да | Да |
| Синоним | Да | Да, кроме команд и групп команд |
| Представление объекта | Да, если свойство есть | Нет |
| Представление списка | Да, если свойство есть | Нет |
| Расширенное представление | Да, если свойство есть | Нет |

Пример из источника: справочник `_ВерсииШаблонов`. Подчёркивание в техническом имени и синониме отличает добавленный объект; в пользовательские представления его не переносить.

Для нового отчёта или обработки дополнительно:

1. Отключить использование стандартных команд.
2. Создать отдельную команду запуска: `ЗапускОтчета` или `ЗапускОбработки`.
3. Синоним команды заполнить названием отчёта или обработки без начального подчёркивания.

Примечание к источнику: общее правило требует подчёркивания в имени, а имена команд запуска приведены без него. Эта неоднозначность корпоративного текста сохранена явно; конкретное имя команды сверять с действующим соглашением соответствующей конфигурации.

Источник: [Оформление имён и синонимов объектов метаданных](https://wiki.spb.teremok.ru/pages/viewpage.action?pageId=163548215).

### Подсистемы и роли новых объектов

Новые справочники, документы, журналы документов, отчёты, обработки, планы видов характеристик, планы счетов, планы видов расчёта, регистры сведений и команды включать в подсистему, входящую в командный интерфейс.

Добавленный объект должен быть доступен хотя бы в одной роли, отличной от роли «Полные права».

В комментарии к задаче на перенос изменений указывать подсистему и роль, в которые включён новый объект. Если объект служебный и не должен быть доступен из интерфейса либо пользователям без полных прав, отдельно отметить это исключение в комментарии к задаче.

После появления объекта в рабочей базе разработчик проверяет его наличие в интерфейсе и доступность тем пользователям, для которых он предназначен. При необходимости добавляет нужные роли в их профили.

Источник: [Включение объекта в подсистемы и роли](https://wiki.spb.teremok.ru/pages/viewpage.action?pageId=163548218).

### Планы обмена

Для нового объекта, который может участвовать в обмене данными, обязательно анализировать необходимость включения в планы обмена `Полный` и `ОбменУППУПП`.

Если по замыслу объект не должен участвовать в обмене, оставить в задаче отдельный комментарий с обоснованием.

При добавлении нового плана обмена предоставить право на его чтение роли `_Пользователь`.

Источники: [Включение объекта в планы обмена](https://wiki.spb.teremok.ru/pages/viewpage.action?pageId=163548219), [Добавление нового плана обмена](https://wiki.spb.teremok.ru/pages/viewpage.action?pageId=163548220).

### Отчёты на СКД и общая форма

Отчёты конфигурации реализовывать с использованием схемы компоновки данных.

В «Оперучёте» интерфейс общей формы отчётов принят как стандартный. По умолчанию рекомендуется использовать эту форму, при необходимости развивая её, и не создавать для каждого отчёта собственную форму.

Если специфика отчёта требует отдельной формы, создавать её на основании общей и сохранять как минимум:

1. Выполнение отчёта в фоне.
2. Запись замеров времени АПДЕКС при формировании отчёта из формы.
3. Разворачивание и сворачивание группы настроек отчёта.

Источник: [Особенности разработки отчётов](https://wiki.spb.teremok.ru/pages/viewpage.action?pageId=163548221).

## Роли и права доступа

### Элементарные функции и атомарные роли

Права строить на атомарных ролях, дающих доступ к элементарным функциям. Из ролей формировать профили, которые назначаются пользователям.

Объекты объединять в одну элементарную функцию, только если не может возникнуть задачи предоставить к ним разный доступ. Каждый объект относить ровно к одной элементарной функции. При сомнении разделять функции.

Пример объединения: «Заказ клиента», отражающий состояние его табличной части регистр «Заказы клиентов» и отчёт по остаткам этого регистра.

Пример разделения: «Реализация товаров и услуг» и регистр «Товары к отгрузке», если кладовщику нужно читать регистр без доступа к документу.

Для функций со ссылочными объектами и независимыми регистрами сведений создавать две роли:

- `_Чтение<ИмяФункции>`.
- `_ДобавлениеИзменение<ИмяФункции>` либо `_Изменение<ИмяФункции>`, если добавление выполняется автоматически или только администратором.

Состав прав, когда они предусмотрены объектом:

| Роль | Права |
| --- | --- |
| `_Чтение<ИмяФункции>` | Чтение, Просмотр, Ввод по строке |
| `_Изменение<ИмяФункции>` | Все права чтения; Изменение и Редактирование; для документов — Проведение, Отмена проведения, Интерактивное проведение, Интерактивная отмена проведения, Интерактивное изменение проведённых; для регистров — Управление итогами |
| `_ДобавлениеИзменение<ИмяФункции>` | Все права роли изменения; Добавление, Интерактивное добавление, Интерактивная пометка удаления и Интерактивное снятие пометки удаления |

Таблица показывает наследование состава прав по смыслу стандарта; она не требует создавать одновременно все три роли для каждой функции.

Источник: [Настройка ролей и прав доступа](https://wiki.spb.teremok.ru/pages/viewpage.action?pageId=163548235).

### Журналы, подсистемы и отчёты

Журнал документов включать в ту же элементарную функцию, если все его документы относятся к ней. В противном случае выделять другую функцию с отдельной ролью.

Для каждой подсистемы верхнего уровня главного командного интерфейса создавать роль `_Подсистема<ИмяПодсистемы>` с правом просмотра.

Для отчётов:

- Если данные относятся к одной функции, в общем случае включать доступ к отчёту в роли этой функции.
- Если нужно отдельно ограничивать отчёт, создавать `_ПросмотрОтчета<ИмяОтчета>` с правами использования и просмотра, даже если данные относятся к одной функции.
- Если данные относятся к нескольким функциям, создавать отдельную роль `_ПросмотрОтчета<ИмяОтчета>` с правами использования и просмотра.

Однотипные отчёты допустимо объединять в элементарную функцию, если они не входят в другие функции и не может понадобиться раздельная настройка доступа к ним.

Источник: [Настройка ролей и прав доступа](https://wiki.spb.teremok.ru/pages/viewpage.action?pageId=163548235).

### Обработки и команды

Для обработки, работающей с данными одной элементарной функции, права просмотра и использования предоставлять ролями этой функции.

Для обработки — рабочего места, работающей с данными нескольких функций, создавать отдельную роль `_ИспользованиеОбработки<ИмяОбработки>` с правами просмотра и использования. Не объединять доступ к разным таким рабочим местам в одной роли.

В роли `_Пользователь` назначать права на:

- Вспомогательные обработки, открываемые только из других объектов, а не из глобального командного интерфейса.
- Обработки с кодом общих печатных форм.
- Обработки общей функциональности.

Для команд, которые не меняют данные, право просмотра назначать роли чтения объекта и роли его изменения. Для команд, связанных с изменением данных, право просмотра назначать роли изменения.

Источник: [Настройка ролей и прав доступа](https://wiki.spb.teremok.ru/pages/viewpage.action?pageId=163548235).

## Транзакции, ошибки и безопасность

### Транзакции и блокировки

- Делать транзакцию минимальной по времени и объему.
- Не выполнять внутри транзакции интерактивные действия и длительные внешние вызовы.
- Гарантировать фиксацию при успехе и отмену при ошибке.
- Блокировать только необходимые данные до ответственного чтения.
- Не подавлять исключение после отмены транзакции, если вызывающий код должен узнать об ошибке.

ИТС: [транзакции](https://its.1c.ru/db/v8std/content/783/hdoc), [управляемые блокировки](https://its.1c.ru/db/v8std/content/460/hdoc), [ответственное чтение](https://its.1c.ru/db/v8std/content/648/hdoc).

### Исключения и журналирование

- Перехватывать только исключения, которые код может обработать или дополнить контекстом.
- Не оставлять пустой блок `Исключение` и не возвращать успех после фактической ошибки.
- При повторном вызове исключения сохранять исходную диагностику.
- Записывать операцию, идентификатор сценария и достаточное описание ошибки.
- Не журналировать пароли, токены, данные карт и избыточные персональные данные.
- Не использовать `Сообщить()` вместо технического журналирования серверной ошибки.

ИТС: [перехват исключений](https://its.1c.ru/db/v8std/content/499/hdoc), [вызов исключений](https://its.1c.ru/db/v8std/content/790/hdoc), [Журнал регистрации](https://its.1c.ru/db/v8std/content/498/hdoc).

### Интеграции и безопасность

- Проверять бизнес-условия до внешнего вызова; непередаваемые документы фильтровать на единой границе интеграции.
- Задавать конечный таймаут. Раздельно обрабатывать сетевую ошибку, HTTP-статус и некорректный ответ.
- Не хранить новые пароли, токены и ключи в коде; использовать защищенное хранилище или настройку.
- Формировать JSON/XML штатными средствами и проверять обязательные поля ответа.
- По возможности обеспечивать идемпотентность повторной отправки.
- Проверять входные параметры экспортных серверных методов и HTTP-сервисов.
- Не применять привилегированный режим без необходимости.
- Не выполнять `Выполнить` и `Вычислить` со строками из внешних данных.

ИТС: [таймауты](https://its.1c.ru/db/v8std/content/748/hdoc), [хранение паролей](https://its.1c.ru/db/v8std/content/740/hdoc), [внешние ресурсы](https://its.1c.ru/db/v8std/content/794/hdoc), [серверный API](https://its.1c.ru/db/v8std/content/678/hdoc), [Выполнить и Вычислить](https://its.1c.ru/db/v8std/content/770/hdoc).

## Работа с хранилищем и выпуск изменений

Корпоративные процедуры ниже описывают порядок работы. Выполнение операций в конкретной базе допускается только после разрешения, предусмотренного [общими правилами](workflow.md#подключения-к-базам-данных--только-с-разрешения-пользователя).

### Захват объектов

Захватывать в хранилище разработки только необходимые объекты. Если изменяется только форма, не захватывать весь объект рекурсивно.

Держать изменённый объект захваченным до переноса изменений в хранилище рабочих баз. По источнику ежедневная автоматическая процедура приравнивает незахваченные объекты хранилища разработки к рабочему хранилищу: незахваченные и ещё не перенесённые изменения могут быть затёрты.

Если другому разработчику нужен захваченный объект:

1. Обсудить приоритет и совместимость изменений.
2. Договориться об отмене изменений с отменой захвата либо о передаче объекта вместе с изменениями, которые допустимо перенести в рабочую базу.
3. Разработчику, инициирующему перенос, проверить работоспособность всего объекта, включая изменения первого разработчика.
4. Если договориться не удалось, передать решение о приоритете архитектору либо проектному комитету.

Источник: [Процесс работы над задачами](https://wiki.spb.teremok.ru/pages/viewpage.action?pageId=163548237).

### Проверка и перенос в рабочую базу

Общий порядок из источника:

1. После выполнения задачи разработчик обновляет тестовые базы СПб и МСК из хранилища разработки.
2. Самостоятельно проверяет функциональность в тестовой базе. Тестировать обязательно в тонком клиенте; толстый клиент в режиме управляемого приложения для этой проверки не использовать.
3. Переводит задачу Jira в статус «Тестирование». Порядок распространяется на проектные задачи и поддержку.
4. Проверяющий тестирует задачу либо передаёт пользователям. При успехе переводит в «ожидает обновления», при ошибках — в «В работе» с описанием несоответствий в комментариях.
5. После исправления ошибок разработчик повторяет цикл с обновления тестовых баз.
6. Для задачи в статусе «ожидает обновления» разработчик добавляет комментарий со списком переносимых объектов. Для новых объектов и команд указывает подсистемы и роли доступа.
7. Ответственный переносит перечисленные объекты в хранилище рабочей базы.
8. На следующий день разработчик проверяет, что все изменения попали в рабочую базу и работают, как минимум доступны в интерфейсе нужным пользователям. После этого освобождает перенесённые объекты в хранилище разработки.

По источнику список объектов принимается до 17:00 в пятницу и до 18:00 в остальные рабочие дни. Поступившие позднее комментарии обрабатываются на следующий день.

Если при переносе обнаружены нарушения стандартов, ответственный оформляет задачу Jira на их устранение; по источнику её требуется выполнить на следующий день.

В исходном процессе проверяющая названа Анной, а перенос описан от первого лица без указания должности или имени ответственного. Текущие ответственные, названия статусов, расписание и действие процедуры синхронизации из пункта 12 требуют подтверждения владельцем процесса.

Источник: [Процесс переноса изменений в рабочую базу](https://wiki.spb.teremok.ru/pages/viewpage.action?pageId=163548234).

### Тестирование отчётов без изменения данных

Корпоративный источник допускает проверку пользователями на рабочей базе только для доработок отчёта, у которого нет функциональности изменения данных.

Если заказчик имеет право открывать внешние обработки, ему можно передать внешний отчёт для проверки. После подтверждения корректности отчёт встраивается по стандартному порядку переноса, без проверки в тестовой базе.

Если права на открытие внешних отчётов нет:

1. Добавить доработанный отчёт в конфигурацию с постфиксом `_Тест` в имени и ` (Тест)` в синониме запускающей команды.
2. Разместить его в интерфейсе и перенести в рабочую базу по стандартному порядку.
3. После успешной проверки заменить существующий отчёт новым, а тестовый удалить.
4. Перенести изменения в хранилище рабочих баз по стандартному порядку.

Если тестовый отчёт временно невозможно удалить, например из-за захваченных ролей, источник предписывает изменить `_Тест` на `_Уделить` и удалить объект позже. Написание `_Уделить` сохранено буквально: вероятная опечатка требует подтверждения, автоматически заменять её на `_Удалить` нельзя.

Это изложение исключения из корпоративного процесса, а не разрешение на подключение или выполнение действий в конкретной базе.

Источник: [Исключения при тестировании отчётов](https://wiki.spb.teremok.ru/pages/viewpage.action?pageId=163548234).

### Хранилища и планирование обновлений

В корпоративном разделе есть отдельные таблицы путей к хранилищам для рабочих баз и для разработки. Их назначение — выбор хранилища по конфигурации и офису; это сведения об инфраструктуре, а не правила оформления кода.

Адреса и учётные имена приведены в корпоративном справочнике. В общей библиотеке сохраняются ссылки; параметры подключений хранятся локально в проектах.

- [Хранилища конфигураций рабочих баз](https://wiki.spb.teremok.ru/pages/viewpage.action?pageId=163548223).
- [Хранилища конфигураций для разработки](https://wiki.spb.teremok.ru/pages/viewpage.action?pageId=163548224).

Порядок планирования обновления из корпоративной инструкции:

1. Открыть базу «Центр администрирования», указанную в источнике.
2. Запустить внешнюю обработку `ЭкземплярыСценариевАвтоматизации`.
3. Выбрать нужные базы, нажать «Запланировать обновление» и указать дату.
4. Проверить, что запланированные базы поднялись наверх списка и отмечены значком часов.

Инструкция со снимками экрана и адресом базы: [Центр администрирования. Планирование обновлений](https://wiki.spb.teremok.ru/pages/viewpage.action?pageId=163548238).

Подключения и планирование обновлений выполнять по соответствующим навыкам и с разрешением пользователя на конкретные действия.

## Проверка результата

Перед завершением доработки:

1. Просмотреть `git diff` затронутых файлов и исключить случайные изменения кодировки и окончаний строк.
2. Выполнить доступную синтаксическую проверку BSL и проверку конфигурации; отсутствие инструмента указать в отчете.
3. Проверить основной, граничный и отрицательный сценарии.
4. Для запроса проверить пустой результат, несколько строк и объемный набор данных, если применимо.
5. Для интеграции проверить успех, таймаут, ошибочный HTTP-статус и некорректный ответ.
6. Убедиться, что поведение несвязанных операций не изменилось.
7. В отчете указать измененные файлы, результат и выполненные проверки.
8. Проверить обязательные описания методов в ПрограммныйИнтерфейс, а также достаточность пояснений к сложным служебным методам.
9. Проверить личные требования к оформлению и маркировку всех изменённых фрагментов.
10. Для новых объектов проверить подсистемы, роли, обмены и доступность пользователям.

### Сохранение исходников и идентификаторов

- Конфигурация хранится в XML/BSL-выгрузке: не выполнять массовое форматирование без необходимости.
- Сохранять кодировку и окончания строк изменяемого файла.
- Не удалять существующие маркированные фрагменты без отдельного требования, кроме собственных устаревших строк кода, добавленных в рамках текущей задачи (см. [личные стандарты](personal-standards.md#сохранение-прежнего-кода)).
- Не изменять автоматически сгенерированные идентификаторы в `ConfigDumpInfo.xml` и XML метаданных.
